# B16 keyword visual routing and catalogue-first simulations

Date: 2026-10-16. Numbered steps and acceptance statuses belong to [STAGES-STEPS.md](../STAGES-STEPS.md#b16--keyword-visual-routing-and-catalogue-first-simulations).

## Response policy

`decision_engine/visual/routing.py:decide_response_visual` is the shared response-policy entry point. Both prompt construction and simulation follow-up use its structured result. `decision_engine.POLICY_VERSION` is now `visual-keywords-4`; prompt versions retain `-visual1`. These intentional behavior changes supersede the B15 extraction-only visual baseline while leaving its historical fixture intact.

| Query / selected context | Result |
| --- | --- |
| Mathematics goal, with or without a visual command | Markdown explanation with KaTeX notation and suitable trusted mathematics activities; chart combinations when explicitly relevant. |
| Study Science/Physics, “Explain gravity” | Text/formulas; no generated activity, chart, inline image or automatic media card. |
| Study Gravity, “show”, “showme” or “show me” | Resolve the validated selected topic, try a matching published interactive, then use Matter if generation is needed. |
| “Create a 3D solar system” | Try a sufficiently relevant 3D-described authored interactive first, then use Three.js. |
| “Show photosynthesis”, no compatible authored interactive | Keep the explanation; do not invent an unrelated physics simulation. |
| “Show gravity, text only”, “no animations”, “don't show”, “without a visual” | Text/formulas; explicit opt-outs take precedence over visual keywords and mathematics activities. |

Positive vocabulary includes the owner's `show`, `showme`, `show me`, `simulate`, `visualization`, `visualisation`, `visual`, `interactive`, `interactivity` and `create`, plus the existing explicit animation/drawing/rotation verbs. Case and whitespace normalize; creation verbs do not accidentally match “creatures”. This is lexical English intent matching, not a general multilingual or semantic classifier. Current response-language support remains intact. Mathematics goals take priority over the science default; merely including a number in a science explanation does not request a simulation.

Ordinary Study science is text until a positive visual request. Mathematics renders notation through existing KaTeX; fractions/counting/shapes use Konva, geometry uses JSXGraph, functions/coordinates use Mafs and data charts use Recharts. The policy permits at most three distinct suitable trusted activities, with existing parameter/grade limits and answer character/word budgets. Duplicate templates and disallowed visuals are filtered before saving. Libraries remain lazy loaded; every answer does not load every library.

Default generated physics is Matter for 2D mechanics and Three for 3D. Existing named R3F/Phaser/Rive/HTML5 requests remain supported outside Study science; Study science generation is limited to compatible physics/3D engines. General science requests can still use a matching authored simulation even when procedural generation has no appropriate engine.

## Ownership and execution

- **Pure policy:** `decision_engine/visual/{keywords,routing,mathematics,simulation,media}.py` handles lexical preference, response format, template/engine choice and deterministic catalogue relevance. It accepts shared DTOs, never imports database, functional or application services.
- **Functional media delivery:** `functional/resources/simulations.py` rechecks published ancestry/revision, current eligible mapping, availability, version, grade/language suitability and self-contained HTML delivery. It uses the existing validated document loader, private storage and CSP. It never ranks or calls a model.
- **Application coordination:** teaching prompt/answer/simulation services coordinate the shared plan, provider and persistence. `teaching/visual_media.py` retrieves eligible candidates and passes them to the pure selector, then opens only the chosen ID/version through the functional service. Existing Study context validation remains authoritative. Curiosity catalogue lookup uses its existing published-name matching, without binding the open answer to a curriculum.
- **Frontend:** `ResponseSimulation` renders authored documents with the existing `InteractiveExperience` opaque-origin `sandbox="allow-scripts"` player. Generated sources still use the worker/compiler sandbox. The authored HTML is never submitted as generated source. The right-side Explore listing is unchanged.

Flow: finish and save the text answer → independently request its simulation outcome → recheck ownership/context → retrieve eligible authored interactives → select a sufficiently relevant one → deliver its isolated document; if no match exists and a suitable engine is selected, use the existing bounded transient generation opportunity.

Matching requires a resource/interactive HTML candidate with current available state, concept overlap and suitability. The question supplies the concept; a short “show me” uses the selected topic/subtopic. Structured concepts/synonyms participate in relevance. Explicit 3D requests require a 3D-described catalogue candidate rather than silently substituting a generic 2D activity. Ties use stable candidate IDs. Unsupported/external/video resources are not executed as authored HTML simulations.

## Saved results, retries and failure behavior

The answer request's existing JSON result stores `visual_routing`, including language, so prompt behavior and the subsequent simulation endpoint agree. Selecting a catalogue source stores only its ID/version and validated path/revision in internal `simulation_source` metadata. Generated fallback records its selected engine. No model-authored source or catalogue document is added to message/request storage; no table or migration is introduced.

Source choices are pinned per answer. Reopening a catalogue choice rechecks the same ID/version/path and does not rerank. A withdrawn or changed source returns unavailable rather than silently launching a paid fallback. Study source snapshots cannot point outside the current validated Study context. Internal follow-up metadata is omitted from the public answer on exact-key replay, preserving the original response and avoiding another provider call.

Authored simulation reuse works without an available model gateway and consumes no generation quota. A missed catalogue match may generate only through the existing fresh-answer arm, start flag, member/admin quota, four-job concurrency limit and bounded cache. Retrieval-only history/check requests cannot start a new job or rearm it. Provider calls occur after the database transaction closes, and short Study requests include validated topic names as bounded data for generation. Cached job results retain their own engine rather than being relabelled by a newer policy.

Automatic recommendation coordination receives the saved policy flag through its owned conversation snapshot. Plain Study science and explicit text-only answers suppress automatic media retrieval/display; sandbox simulation answers suppress duplicate media cards. Teacher/kit selection and independent Explore browsing retain their existing contracts and access checks. Existing answers without the new routing metadata retain the legacy recommendation behavior.

The browser does not retain authored HTML in the global generated-job cache after delivery. Every remount/reopen therefore rechecks current server authorization/version; only the active isolated viewer holds its document. Existing generation recovery/deadline behavior remains unchanged.
